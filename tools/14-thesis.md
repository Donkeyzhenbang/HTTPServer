## 第一章 绪论

### 1.1 研究背景与意义

**痛点分析（论文立论基础）：**
- 电力输电通道巡检中，弱光/逆光场景图像预处理效果差，传统 ISP pipeline 无法有效恢复暗区细节
- 真实场景的缺陷图像样本稀缺，公开数据集（CPLID 等）与现场场景存在分布偏移
- 边缘部署的检测模型无法迭代更新：新出现的缺陷类型无法识别，模型精度随时间衰减
- 现有巡检系统缺乏从数据采集到模型更新的端到端闭环

**学术价值：**
- 将 HDR 图像增强引入电力巡检领域，解决弱光场景图像质量瓶颈
- 探索云边协同架构在工业视觉闭环系统中的工程实践
- 系统性地构建训练-部署-测试-反馈-升级全链路

### 1.2 国内外研究现状

| 方向 | 相关工作 | 不足 |
|------|----------|------|
| HDR 图像增强 | DeepFuse, AHDRNet, LFM/CRM 系列 | 未针对电力场景优化，推理延迟高 |
| 电力缺陷检测 | YOLO 系列在 CPLID 数据集上的应用 | 缺乏弱光场景适配 |
| 云边协同 | KubeEdge, Azure IoT Edge | 侧重通用框架，缺乏 AI 模型闭环能力 |
| 模型热更新 | TensorFlow Serving, Triton | 重型框架，不适用边缘嵌入式设备 |

### 1.3 研究内容

1. **C++ 高性能设备网关** — 基于 epoll reactor + 线程池的并发通信层，支持私有二进制协议
2. **弱光图像 HDR 增强引擎** — LFM_V1（亮度融合）+ CRM_V1（色彩恢复）双模型推理
3. **多 GPU 并发推理调度** — 动态批处理 + GPU 显存管理
4. **分布式协同管理** — 基于 ZooKeeper 的服务发现、主节点选举、配置下发；基于 Redis 的会话管理
5. **模型闭环迭代链路** — 离线协议握手、mmap 零拷贝模型传输、断点续传、网关心跳管理

## 第三章 C++高性能设备网关设计 [核心]

> 当前完成度：~80%

### 3.1 基于 epoll 的事件驱动架构

**设计要点：**
- 单线程 epoll_wait 循环监听最多 1000 个 fd
- 使用 EPOLLET 边缘触发模式，配合非阻塞 I/O
- 通过 EPOLLRDHUP 感知对端断开，触发连接清理

```cpp
// EventLoop 核心接口
void AddSocket(int fd, uint32_t events, EventCallback cb);
void Run();       // 阻塞式事件循环
void Stop();      // 优雅退出
```

**关键技术挑战与解决：**
- **挑战1：ET 模式下的数据完整读取** — while(true) 循环 read 到 EAGAIN 为止
- **挑战2：回调重入问题** — 拷贝回调后再执行，不持有锁调用用户函数
- **挑战3：大量超时/断线检测** — 心跳包走 IO 线程 Fast Path，零上下文切换

> 插图：epoll 事件循环状态机图

### 3.2 线程池并发处理模型

**设计要点：**
- 固定大小线程池（4 worker），std::queue + mutex + condition_variable
- is_processing 原子标记，保证同一连接同时只有一条任务在处理
- 缓冲区锁与处理锁分离，IO 线程读取时持锁时间极短

**处理流程：**
```
IO线程: read → buffer → CAS(processing_flag) → enqueue(λ)
                                          │
工务线程池: dequeue → ProcessConnection → 协议解析 → dispatch → 回复
```

> 当前已实现，未来可优化为多级队列：心跳/数据/命令按优先级处理

### 3.3 私有二进制协议设计

**帧格式定义：**

| 字段 | 偏移 | 长度 | 说明 |
|------|------|------|------|
| Sync | 0 | 2 | 同步头 0x5AA5 (Little Endian: A5 5A) |
| Packet Length | 2 | 2 | 整包长度，小端序 |
| CMD ID | 4 | 17 | 设备唯一标识（16字符 + NULL） |
| Frame Type | 21 | 1 | 帧类型 |
| Packet Type | 22 | 1 | 包类型 |
| Payload | 23 | N-25 | 载荷 |
| CRC | N-2 | 2 | 校验 |
| End | N | 1 | 尾标识 |

**协议注册机制：**

```cpp
struct HandlerFun {
    u_int8 frameType;
    u_int8 packetType;
    int (*func)(unsigned char* pBuffer, int Length, int fd);
};

static HandlerFun Handlers[] = {
    {0x09, 0xE6, HandleHeartbeat},  // 心跳
    {0x05, 0xEF, HandleFileStart},  // 文件传输开始 (B351)
    {0x05, 0xF0, HandleFileData},   // 文件数据块 (B352)
    {0x05, 0xF1, HandleFileEnd},    // 文件传输结束 (B37)
};
```

**协议分包重组：**
- 同步头扫描（FindSyncHeader）：跳过损坏字节，定位 0x5AA5
- 长度校验：packetLen 在 [4, 4096] 区间，否则丢弃并继续扫描
- 粘包/半包处理：缓冲区保留不完整包，等待下次 epoll 触发
- 分包乱序处理：使用 recvStatus bitmap 标记，B37 结束时统计缺失率

### 3.4 心跳快路径优化

**设计动机：** 电网站点设备数量多（可至数千），心跳包频率高（15-30s 间隔），若每个心跳都走线程池入队-出队路径，将产生大量上下文切换。

**实现：** OnClientRead 中检测到 `n==28 && inputBuffer.empty()` 且 Header/Type 匹配心跳特征时，IO 线程直接调用 SendHeartbeatResponse 回包，零入队开销。

**效果预估：** 心跳响应延迟从 ~10ms（含线程调度）降至 ~50μs（纯 write 系统调用）

### 3.5 连接生命周期管理

```
connect → handleNewConnection:
            - fcntl O_NONBLOCK
            - create_connection_context
            - eventLoop.AddSocket(EPOLLIN | EPOLLET | EPOLLRDHUP)
            └── 等待数据

heartbeat → Update:
              - setDeviceId (提取 CMD ID)
              - Redis SET device:online:<id>, TTL=180s
              - 触发分布式协调

transfer → B351(start) → B352(data)×N → B37(end) → B38(ack):
              - 接收时：mmap → write to buffer[offset]
              - 结束时：统计缺失率 → 写入磁盘
              - 清理：释放 buffer，状态回到 IDLE

disconnect → EPOLLRDHUP:
              - eventLoop.RemoveSocket
              - close(fd)
              - remove_connection_context
              - Redis DEL device:online:<id>
```

## 第四章 分布式协同管理

> 当前完成度：~70%

### 4.1 基于 ZooKeeper 的服务发现与主节点选举

**ZK 目录结构设计：**
```
/gw-server/
├── nodes/             # 服务节点注册（Ephemeral 节点）
│   ├── node_10.0.0.1_52487
│   └── node_10.0.0.2_52487
├── election/master/   # 主节点选举（Sequential Ephemeral 节点）
│   ├── candidate_0001
│   └── candidate_0002 ← 最小序号 = master
├── config/            # 分布式配置
│   ├── hdr_threshold  # HDR 处理阈值
│   └── model_version  # 当前模型版本
└── locks/             # 分布式锁
    └── device_xxx     # 设备级互斥锁
```

**主节点选举算法：**
- 创建 ZOO_SEQUENCE | ZOO_EPHEMERAL 节点
- 获取 /election/master 下所有子节点，按字典序排序
- 最小序号节点当选 master
- 通过 Watcher 监听节点变化，master 下线时自动触发新一轮选举

### 4.2 基于 Redis 的设备会话管理

**数据结构：**
```
Key:   device:online:<device_id>
Value: {"ip":"10.0.0.1","port":52487,"http_port":8080}
TTL:   180s（3倍心跳间隔，保证心跳间隙内记录有效）
```

**用途：**
- 设备归属查询：前端请求设备时，查询 Redis 确定设备连接在哪台网关节点
- 心跳监控：TTL 过期 → 路由 APP 检测到设备离线 → 推送告警

### 4.3 分布式设备锁

**设计动机：** 多网关场景下，同一设备只能被一台网关服务的线程处理（特别是模型升级操作）。

**实现：**
- AcquireLock("device_xxx", timeout=3000ms)：ZK 顺序临时节点 + 监听前序节点
- 设备在本地 → 拥有锁 → 执行操作 → 释放
- 设备在远端 → 尝试远程调用或等待

## 第五章 HDR 图像增强与 AI 推理服务

> 当前完成度：~75%

### 5.1 双曝光 HDR 融合模型

**问题定义：**
弱光场景下单帧图像信噪比低，信息丢失严重。传统方法（直方图均衡、Gamma 校正）存在暗区过曝/亮区欠曝问题。

**技术方案：**
采用 LFM_V1（亮度融合）+ CRM_V1（色彩恢复）两阶段模型：

```
 低曝光图像 Img1 ──┐
                    ├──► Y 通道提取 → [Img0, Img1] → LFM_V1 → Output_Yf
 高曝光图像 Img2 ──┘                                    │
                                                        ▼
                                                色彩空间转换 YCbCr
                                                        │
                        [Img1_YCbCr, Img2_YCbCr, Output_Yf] → CRM_V1 → Output_CbCr
                                                        │
                                                        ▼
                                                YCbCr → RGB → HDR 输出
```

**模型推理流程：**
1. 双曝光图像预处理：BGR→RGB → [0,1] 归一化 → Tensor to GPU
2. LFM_V1 前向：输入 [1,2,H,W] 双 Y 通道 → 输出 [1,1,H,W] 融合亮度
3. CRM_V1 前向：输入 [1,7,H,W] 双图 YCbCr + 融合亮度 → 输出 [1,2,H,W] 色度
4. 后处理：YCbCr→RGB → [0,255] → JPEG 编码 → Base64 输出

### 5.2 动态批处理调度

**设计动机：**
GPU 推理的批处理吞吐高于逐张推理，但等待过久会增加延迟。

**实现（DynamicBatcher）：**
- 双阈值策略：max_batch_size (上限) + max_wait_ms (最大等待)
- 收集逻辑：循环从 Queue 取请求，达到上限或超时则执行
- 多分辨率对齐：过小图像先 bilinear resize 到批次最大尺寸

**性能数据（预估）：**
- 单张推理：45ms
- 4 张批量推理：75ms（18.8ms/张，节省 58%）

### 5.3 GPU 显存管理

**设计要点：**
- 每 N 次推理触发一次周期性清理（gc.collect() + torch.cuda.empty_cache()）
- 后台监控线程周期性检查显存占用率：
  - > 85%：告警日志
  - > 90%：强制清理
- MemoryGuard 上下文管理器包装推理调用，自动采样与清理

## 第六章 模型闭环迭代机制 [核心]

> 当前完成度：~60%

### 6.1 闭环迭代总体方案

**闭环链路：**
```
┌─────────────────────────────────────────────────────────────┐
│  ① 采集        ② 预处理推理    ③ 数据反馈     ④ 再训练     ⑤ 热更新
│                                                     │
│  边缘设备 ──► 网关透传 ──► HDR+Yolo ──► 置信度<阈值 ──► 云端Ray
│      ▲              ▲                         │          │
│      │              │                         ▼          ▼
│      └────── ⑥ 新模型部署 ◄────── B351-38 ◄── 模型文件 (.pt)
│                                                     
└─────────────────────────────────────────────────────────────┘
```

**闭环触发条件：**
- **数据驱动：** 低置信度（conf < 0.5）样本数累积 ≥ N（如 500 张）→ 触发再训练
- **时间驱动：** 固定周期（如 7 天）全量数据再训练
- **模型驱动：** 验证集 mAP 下降 ≥ 2% → 回滚上一版本

### 6.2 设备端模型热更新协议

**握手流程（B351-B352-B37-B38 四阶段）：**

```
T0: 网关 ──B351(channelNo, packetLen)──► 设备   [传输开始通知]
T1: 网关 ◄──B352(Ack)────────────────── 设备   [设备确认就绪]
T2: 网关 ──PhotoData×N────────────────► 设备   [数据块发送, mmap 零拷贝]
T3: 网关 ──B37(校验信息)──────────────► 设备   [传输结束 + 完整性校验]
T4: 网关 ◄──B38(Ack)────────────────── 设备   [设备确认接收完毕]
```

**关键设计：**
- mmap 零拷贝：模型文件通过 mmap 映射为 virt addr，避免用户态-内核态拷贝
- 分块发送：1024 字节/包，防止大文件阻塞其他连接
- 丢包统计：recvStatus bitmap 记录每包接收状态，B37 结束时统计缺失率
- 断点续传：设备端可重新发起传输，网关从指定 offset 续传

### 6.3 数据回流与云端再训练

**数据采集链路：**
```
设备拍照 → 网关接收(recvfile) → 保存本地(/uploads/) → 前端标注 → 
→ 导出标注数据 → SCP/API 推送到训练服务器
```

**云端训练（基于 Ray）：**
```
Ray Cluster
├── Head Node: 任务调度 + 数据分发
├── Worker 1: YoloV5 训练任务
├── Worker 2: HDR 模型 finetune
└── Worker N: 超参搜索
```

**当前状况与规划：**
- 当前：手动导出标注数据 → 手动运行训练脚本 → 手动部署
- 规划：低置信度图像自动归档 → Redis 队列通知 → Ray 自动触发训练 → 训练完成回调触发模型升级

### 6.4 模型版本管理与回滚

**当前设计（客户端）：**
```
客户端 modelupgrade.cpp:
  - 从网关接收模型文件
  - 保存本地备份（版本号时间戳）
  - 原子替换活跃模型文件（rename 保证原子性）
```
